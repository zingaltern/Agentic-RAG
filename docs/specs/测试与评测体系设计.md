## 0. 摘要

**现状判断**：项目已有较完整的工程回归体系（单测、验证集、外部集、性能基准、冻结集、CI），但**不满足“RAG 质量评测”要求**：

- `make eval` 默认进程内 Stub LLM，测的是检索与兜底，不测真实生成；
- `golden_answer` 在 `rageval.py` 中未被读取，答案正确性没有打分；
- `AnswerRelevancy` = 回答非空；`Faithfulness` = 系统自身 detector 的 `passed` 比例（自评）；
- `complex` 90 条与 CMRC 160 条全部没有标准答案；上下文被截断到 300 字；
- 冻结集 `eval_suite` 与开发集存在完全重复/高相似用例，违反其 README 的“互斥/改述”约定；
- 报告不入库、无数据集/模型/judge 版本溯源、无置信区间，单次点估计直接当结论。

**目标体系**：把测试分成**六个层次**（静态与契约 / 单元 / 组件功能 / 集成与 E2E / 质量评测 / 非功能与生产），把指标分成**四个层级**（硬门禁 / 质量门禁 / 诊断指标 / 运营指标），并引入**独立 judge + 人工校准 + 统计显著性 + 数据资产治理**。RAGAS 作为“语义质量层”的裁判之一，不替换现有回归体系。

**关键变化**（与现状的差异）：

| 变化 | 当前 | 目标 |
|---|---|---|
| 质量结论来源 | 系统自评 + Stub | 独立 judge + 人工校准 + 冻结 holdout |
| 评测数据 | demo/合成，无参考答案 | 生产级语料 + 参考答案 + 证据 chunk + 分层切片 |
| 指标 | 来源级 Hit、非空式 relevancy | IR 指标 + claim 级 Faithfulness/Correctness + 引用 F1 + 兜底正确率 |
| 门禁 | 单测硬门禁；eval 仅留痕 | 硬门禁 + 质量门禁（统计下界）+ 非回归 |
| 统计 | 单次点估计 | 每案得分 + Bootstrap 95% CI + 配对比较 |
| 可复现 | 报告 gitignore、无版本溯源 | 数据集/配置/模型/judge 版本 + 哈希 + 原始 JSONL 归档 |
| 生产闭环 | 基本没有 | 线上指标、影子评测、季度人工审计、漂移告警 |

### 1.2 抽样方法

本次抽样做了六类检查：

1. 全量字段统计：`id/type/variant/query/expected_sources/golden_answer` 的分布与缺失；
2. 来源核对：`expected_sources` 与 `tests/eval/sample_data/` 实际文件逐一比对；
3. 重复/近重复：跨 `tests/eval`、`tests/review`、`tests/eval_suite` 做精确与 `difflib` 相似度比对；
4. 参考答案一致性：标准答案是否为来源文档中的可抽取事实、数字是否一致；
5. 规模与复杂度：语料字数、文档数、查询长度、问句模板分布；
6. 实现静态审查：`rageval.py`、`eval_suite/runner.py`、`orchestration.py` 的指标与数据出口。

### 1.3 抽样发现

#### 1.3.1 规模与复杂度：验证集的 default/docs 是“玩具级”

- `default`：3 份文档、合计 1,089 字（不含 `.DS_Store`）；21 条问题，平均每 50 字一题。
- `docs`：2 份文档、合计 968 字；86 条问题，平均每 11 字一题。
- 两个库的文档都小于 1KB，任何带关键词的检索都很容易全绿；**default/docs “全绿”不能作为质量证据**。
- `complex`：43 份文档、合计 154,147 字，但 29 份 <1KB，只有 14 份 >1KB、9 份 >5KB、6 份 >10KB；语料为“云帆科技”合成域，90 条中 39 条是“多少”型数值题，模板化明显。
- 查询偏短：default/docs/complex 查询长度中位数分别约 16/10/16 字，远低于真实生产问句分布。

#### 1.3.2 结构完整性：字段不一致、参考答案缺失

- `tests/eval/qa_pairs/complex/qa_pairs.jsonl` **90 条全部没有 `golden_answer`**，只有 `id/query/type/variant/expected_sources`；答案正确性完全无法评。
- `tests/review/qa_pairs/cmrc/qa_pairs.jsonl` **160 条全部没有标准答案**，`rageval` 对 CMRC 只算 Hit@1/5 与兜底率。
- `tests/eval/qa_pairs/default/qa_pairs.jsonl` 的 `Q17` 使用 `expected_doc` 而非常规 `expected_sources`（因是 `no_answer`，当前不影响判分，但 schema 不一致）。
- `tests/eval_suite` 用 `golden` 字段，`tests/eval` 用 `golden_answer`，`review` 两者都没有；同一套 runner 无法统一消费。
- `tests/eval_suite/runner.py:129` 的 `answer_key_hit_rate` 只做 `keywords` 字面全命中；`runner.py:130` 的 `faithful_rate` 使用系统自身 `hallucination_check`。

#### 1.3.3 独立性：冻结集与开发集出现重复

- 精确重复：`tests/eval/qa_pairs/docs` 的 `D043`、`D046` 与 `tests/eval_suite/qa_pairs/docs` 的 `DC24`、`DC16` **查询文本完全相同**；同名 `note` 声称“同意图改述”，实际未改述。
- 近重复：抽样比对发现 15 对相似度 ≥0.85 的用例（如 `D065` 与 `DC50`、`D012` 与 `DF12` 等）。
- 这违反 `tests/eval_suite/README.md` 第 2 节“不得整条复制/改写开发集；同意图必须改述并注明”的约定；冻结集因此不能作为完全独立的第二道门禁。

#### 1.3.4 参考答案与证据：只有“文件名”，没有“证据 chunk”

- `tests/eval` 的 `expected_sources` 只到文件名级（CMRC/isolated 相同）；同一文档内检索到错误 chunk 也会算 Hit。
- 没有 `reference_evidence` / `gold_chunk_ids` / `page`，无法计算 chunk 级 Recall@k、MRR、nDCG、ContextPrecision/Recall。
- `golden_answer` 中 33/86 条（docs）长度 ≤8 字，很多是短语（如“二等座”“不计加班”），不足以支撑 RAGAS 的 claim 级 ContextRecall/AnswerCorrectness，需要改写成完整答案。
- 抽样核对未发现系统性事实错误，数字大体与来源一致；问题主要是**粒度不足**与**schema 不统一**。

#### 1.3.5 指标有效性：生成质量指标是代理/自评

- `app/cli/rageval.py:209`：`answer_relevancy = bool(answer.strip()) and "抱歉，暂未找到" not in answer`，只判断“非空且不是兜底”。
- `app/cli/rageval.py:200`：`faithful = hallucination_check == "passed"`，用被测系统自身的幻觉检测器给系统打分。
- `app/cli/rageval.py:202-209`：`ContextPrecision` 是“命中来源的 1/(rank+1) 之和 / 期望来源数”，`ContextRecall` 是“期望来源覆盖率”，都是文档级近似，不是 RAGAS 的上下文级指标。
- `app/cli/rageval.py` 全文没有读取 `golden_answer`；`tests/eval_suite/runner.py` 也不读取 `golden`。
- `app/cli/rageval.py:199` 读取 `data.elapsed_ms`，但进程内模式的 `elapsed_ms` 在响应顶层，导致进程内报告耗时恒为 0（实测确认）。
- `app/cli/rageval.py:259` 的基线解析只匹配 `| 指标 | 12.34% |`，`通过率` 的 `x/y` 不会被比较；`:304` 的 diff 只取第一个 kb 的聚合。
- `app/services/orchestration.py:45` 将 `sources[].chunk` 截断到 300 字，评测拿不到完整上下文。
- `app/cli/rageval.py:147` 对 `docs_dir.iterdir()` 只过滤 `is_file()`，工作区中的 `.DS_Store` 会被尝试入库并产生失败告警（当前不致命，但属于卫生问题）。

#### 1.3.6 自动化与可复现

- CI 已存在，但 `eval` job 为 `continue-on-error: true`，且跑的是 Stub 进程内评测；质量结果不阻断，也没有 judge 校准。
- `reports/` 被 `.gitignore` 忽略；当前工作区未发现报告产物；新 clone 无法复现“首轮基线”。
- 报告没有记录 git SHA、数据集哈希、模型版本、judge 版本、prompt 版本、配置哈希。
- `tests/eval_suite/runner.py` 未接入 `make`，冻结集需要人工执行。
- `docs/dev-tasks/04` 写“CI 基线门禁 ✅ 已交付”，而 `DEVELOPMENT.md` 13.11.3 仍写“⚠️ 未接入 CI”，口径不一致，需要统一。

### 1.4 合格性判定

| 维度 | 结论 | 说明 |
|---|---|---|
| 结构完整性 | ⚠️ 部分合格 | 字段基本齐全，但 schema 不统一、complex/CMRC 缺标准答案 |
| 语料规模 | ❌ 不合格 | default/docs 玩具级；complex 合成且 29/43 <1KB |
| 复杂度覆盖 | ⚠️ 部分合格 | 有表格/多文档/噪声/长文变体，但模板化明显 |
| 独立性 | ❌ 不合格 | 冻结集与开发集存在精确/近重复 |
| 参考答案 | ❌ 不合格 | 大量短语级 golden；无证据 chunk；无 claim 级参考 |
| 指标有效性 | ❌ 不合格 | 生成指标自评/非空；无答案正确性 |
| 统计严谨性 | ❌ 不合格 | 单次点估计，无 CI/显著性 |
| 可复现 | ⚠️ 部分合格 | fresh-kb/seed 有，但报告不入库、无版本溯源 |
| 自动化 | ⚠️ 部分合格 | CI 有单测/前端构建；质量评测不阻断 |
| 独立性（评测者） | ❌ 不合格 | 用被测系统自身 detector 当裁判 |

**总体裁定**：现有评测语料**可作为 smoke/retrieval 回归与压力语料继续使用，但不能作为 RAG 质量结论或发布依据**；需要重建“参考答案 + 证据 + 独立 judge + 统计协议”的质量评测层。

| 资产 | 处置 | 理由 |
|---|---|---|

## 2. 调研结论

### 2.1 外部参考

| 框架/研究 | 核心思想 | 本设计采用 |
|---|---|---|
| Google **ML Test Score**（Breck et al., 2017） | 28 项测试分四类：数据测试、模型测试、基础设施测试、监控测试；每项按“人工/自动化”计分 | 用四类组织质量与生产测试；基础设施测试覆盖“入库可复现、索引可回滚、pipeline 集成、可调试” |
| **CheckList**（Ribeiro et al., ACL 2020） | 行为测试三类：MFT（最小功能）、INV（扰动不变性）、DIR（方向性期望） | 用于检索/兜底/改写/检测的鲁棒性测试；不依赖标准答案，补标注盲区 |
| **RAGAS** | 参考无关 + 参考相关指标：Faithfulness、AnswerRelevancy、ContextPrecision/Recall、AnswerCorrectness 等 | 作为语义质量层主指标库；必须独立 judge、完整上下文、参考答案 |
| **RAGChecker**（Ru et al., 2024） | claim 级 entailment；overall precision/recall/F1；retriever 的 claim recall/context precision；generator 的 context utilization/noise sensitivity/hallucination/self-knowledge/faithfulness；meta-eval 证明比 RAGAS/ARES 更贴近人工 | 借鉴 claim 级 F1、context utilization、noise sensitivity、hallucination 作为诊断指标；不追求单一平均分 |
| **ARES / RGB / CRUD-RAG / MultiHop-RAG** | 组件化评测、鲁棒性（噪声/负拒绝/信息整合/反事实）、中文 CRUD 场景、多跳检索 | 用作外部/扩展评测的候选；先接 CMRC，后续按需接 CRUD-RAG/MultiHop-RAG |
| **DeepEval** | pytest-native 门禁；RAG 指标与 G-Eval；提供 reason | 借鉴其“每指标独立阈值、不混合平均”的工程做法；不强制新增依赖 |
| **LlamaIndex Evaluation** | `RetrieverEvaluator`：hit_rate/MRR/precision/recall/AP/NDCG；Faithfulness/Relevancy/Correctness evaluator | IR 指标自研（零依赖）；LlamaIndex 仅按需接入，不引入第二套 judge 引擎 |
| **LLM-as-Judge 可靠性研究（2025–2026）** | exact-match 一致率会高估；需报告 Cohen's κ；存在位置/冗长/自我偏好偏差；应人工校准、固定 prompt、多次运行 | judge 校准协议：50~100 条人工标注、κ/相关系数、偏差审计、冻结版本；未达标不得作为门禁 |
| **Bootstrap CI（LREC 2022 等）** | 报告置信区间比单点 SOTA 更可靠；1000~5000 次重采样 | 所有质量指标输出 mean + 95% CI；A/B 用配对 bootstrap |
| **合成 vs 真实查询分布（2026）** | 合成查询更长、来源覆盖更偏；合成集 Hit@5 可能显著高于真实查询 | 合成集只做压力/回归；质量结论必须来自真实或人工审校的查询分布 |
| **Hypothesis** | 属性测试：对任意合法输入断言不变量，自动缩小反例 | 用于 parser/chunker/RRF/幂等/边界等确定性模块 |

### 2.2 关键启示

1. **测试不只分“单测/集成”，还要分“数据/模型/基础设施/监控”**；当前缺的恰恰是后三类。
2. **质量指标必须与人工判断做 meta 校准**；同名指标（如 Faithfulness）在不同框架中定义不同，不能互相替代。
3. **参考无关指标不能证明正确性**：Faithfulness 只证明“忠于上下文”，不证明“答对”；必须配 AnswerCorrectness + 证据检索指标。
4. **合成数据不能替代真实分布**：当前 default/docs/complex/CMRC 都是合成或单一来源；需要真实知识库 + 真实问句。
5. **单一 judge、单次运行不可信**：至少固定 judge 版本 + 温度 0 + 多次运行 + 人工校准 + 偏差审计。
6. **门禁要按指标独立设**，不能把 Faithfulness 与 Relevancy 平均成一个“总分”。
7. **统计显著性要前置设计**：每案得分、Bootstrap CI、配对比较、样本量与切片最小 N。
8. **数据即代码**：语料、标注、证据、分割、版本、哈希、变更记录都要进仓库或制品库。

### 2.3 设计原则

1. **分层不混层**：单元测试不碰真实模型；集成测试用真实本地资源；质量评测独立 judge。
2. **功能与质量分离**：功能测试判“行为对不对”，质量测试判“效果好不好”。
3. **独立评测者**：Judge/人工标注器与被测系统解耦；禁止 self-grading。
4. **参考优先**：能拿到参考答案/证据的，优先 reference-based；参考无关指标只作补充。
5. **指标分层**：硬门禁（0/100%）、质量门禁（统计下界）、诊断指标（不设门禁）、运营指标（监控）。
6. **切片报告**：按类型/难度/格式/库/语言分层；聚合值只用于概览。
7. **统计门禁**：质量变化用配对 bootstrap CI 判定，不用单点 Δ。
8. **版本可溯**：数据集、语料、judge、prompt、模型、配置、代码都有版本/哈希。
9. **自动化 + 人工校准**：日常自动跑；关键 judge 定期人工校准；高风险用例人工审计。
10. **成本与隐私约束**：评测有 token/费用预算；外部 judge 前做 PII/敏感信息评估。

## 3. 目标体系总览

### 3.1 六层模型

| 层 | 目的 | 运行时机 | 依赖 | 门禁 |
|---|---|---|---|---|
| L0 静态与契约 | 配置/接口/错误码/OpenAPI 契约不漂移 | PR | 纯 Python | 硬门禁 |
| L1 单元 | 每个模块的确定性行为、边界、属性 | PR | 桩件、tmp | 硬门禁 |
| L2 组件功能 | 单适配器/服务与真实本地资源或真实 API 行为 | PR（快） | 本地资源/TestClient | 硬门禁 |
| L3 集成与 E2E | 上传→入库→检索→问答→引用→删除；多库隔离；故障注入 | PR 慢/夜间 | Chroma/BGE/Stub LLM | 硬门禁 |
| L4 质量评测 | 检索/生成/引用/兜底的真实效果；RAGAS/Judge；外部集 | 夜间/周度/发布 | 真实 LLM（judge）、标注集 | 质量门禁 |

### 5.3 语料规范

- **规模**：目标库 100~500 份文档、10~100MB 文本；覆盖 PDF/DOCX/XLSX/PPTX/HTML/EML/MD/TXT/CSV/JSON/代码。
- **复杂度切片**：单跳/多跳、单文档/跨文档、表格/数值、长文、噪声/OCR、近重复/版本冲突、陈旧文档、域外。
- **硬负例**：与目标文档语义相近但答案不同的文档；近重复文档；同名不同版本。
- **不可回答**：域外、知识库缺失、诱导编造（要求给出不存在的信息）。
- **多轮**：指代消解、话题切换、澄清后追问、历史摘要压缩。
- **安全**：提示注入、越权 kb_id、PII、超长输入、资源耗尽、恶意附件。
- **冻结**：每个 split 生成 `SHA256SUMS`；语料与索引 DNA 绑定；resplit 需变更记录。

### 5.4 标注与治理

1. **指南先行**：明确“答案正确/部分正确/错误”“证据充分/不足”“应兜底/应澄清”的判定规则与示例。
2. **双人标注 + 仲裁**：核心集 100% 双人；D3 至少 30% 双人；分歧由第三人仲裁。
3. **一致性指标**：答案正确性 κ≥0.7、证据定位 κ≥0.7；低于阈值先改指南或降级为“仅供诊断”。
4. **LLM 只做候选**：LLM 可生成候选题/候选证据，但进入测试集前必须人工审校；禁止 LLM 生成即当 ground truth。
5. **变更控制**：数据集版本号 + 变更日志；一旦冻结，修复需记录原因、影响用例、重新生成基线。
6. **泄漏检查**：跨 split 查询/文档查重；prompt/答案不得泄漏进被测评测集；开发集不得复制进 holdout。
7. **答案可验证**：每条 `reference_answer` 的证据必须能在 `reference_evidence` 中逐字定位。
8. **真实优先**：优先真实用户问句（脱敏）；合成只能补充长尾/压力场景，且必须单独打标 `source=synthetic`。

## 6. 指标与判据

### 6.1 指标分层

| 层级 | 用途 | 指标 | 门禁方式 |
|---|---|---|---|
| Tier 0 硬门禁 | 正确性/安全底线 | 契约率、隔离泄漏、鉴权绕过、密钥/PII 泄漏、超时数、5xx、删除级联完整性 | 必须 = 100% / 0 |
| Tier 1 质量门禁 | 用户可感知质量 | Hit@1、Recall@5、nDCG@10、Faithfulness、AnswerCorrectness、AnswerRelevancy、Citation F1、兜底正确率、任务成功率、P95、cost/query | 绝对地板 + 非回归 + 统计下界 |
| Tier 2 诊断 | 定位问题 | ContextPrecision/Recall、claim recall、context utilization、noise sensitivity、hallucination、self-knowledge、改写增益、重排增益、解析保真度 | 只看趋势，不设硬门禁 |
| Tier 3 运营 | 线上健康 | 线上反馈、fallback 率、引用点击率、P50/P95/P99、错误码分布、队列深度、漂移、费用 | 监控/告警 |

### 6.2 核心指标定义

| 指标 | 定义/公式 | 依赖 | 方向 |
|---|---|---|---|
| Hit@k | 任一 gold 证据出现在 top-k 的查询占比 | gold_chunk_ids | ↑ |
| Recall@k | \|检索∩gold\| / \|gold\|，按查询平均 | gold_chunk_ids | ↑ |
| Precision@k | \|检索∩gold\| / k（或检索数），按查询平均 | gold_chunk_ids | ↑ |
| MRR@k | 首个相关结果排名倒数的均值 | gold_chunk_ids | ↑ |
| nDCG@k | DCG@k / IDCG@k（二值或分级相关性） | gold_chunk_ids | ↑ |
| Faithfulness | 被上下文支持的 claim 数 / 总 claim 数 | answer + 完整 contexts | ↑ |
| AnswerCorrectness | claim 级 factual F1 与语义相似度的加权 | answer + reference | ↑ |
| AnswerRelevancy | 由 answer 生成的问题与原始 query 的相似度（RAGAS QAG） | answer + query + embedding | ↑ |
| ContextPrecision | 相关上下文是否排在噪声前面（rank-aware） | query + contexts + reference | ↑ |
| ContextRecall | reference 的 claim 被上下文覆盖的比例 | reference + contexts | ↑ |
| Citation F1 | 引用支持度：precision=被引用句被证据支持数/引用数；recall=被支持句被正确引用数/总支持句数 | answer + citations + contexts | ↑ |
| 兜底正确率 | no_answer/no_invent 按判据正确拒答的比例 | expected_behavior | ↑ |
| 幻觉率 | 含至少一个不被支持 claim 的回答占比（或 claim 级比例） | answer + contexts | ↓ |
| 任务成功率 | 人工/ rubric 判定“解决了用户问题”的比例 | rubric + 人工 | ↑ |
| P95 延迟 | 端到端耗时 P95 | 运行时 | ↓ |
| cost/query | 每查询 token/费用 | 计费日志 | ↓ |
| Judge 一致性 | judge 与人工的 Cohen's κ / Spearman | 人工标注 | 监控 |

> RAGAS 的 C-P/C-R/AnswerCorrectness 需要 `reference`（标准答案），Faithfulness/AnswerRelevancy 不需要；`reference_evidence` 用于 IR 指标与引用指标。不要把同名指标跨框架直接比较。

### 6.3 门禁与阈值（初始建议）

| 组 | 指标 | 初始地板 | 说明 |
|---|---|---|---|
| 硬门禁 | 契约正确率 | 100% | 含非法参数、鉴权、隔离 |
| 硬门禁 | 跨库隔离泄漏 | 0 | 任何泄漏阻断发布 |
| 硬门禁 | 密钥/PII 泄漏 | 0 | 扫描 + 黑盒探针 |
| 硬门禁 | 超时/5xx | 0（或 <0.1%） | 超可接受阈值阻断 |
| 检索 | Hit@1 | ≥0.70 | 按 direct/rewrite/表格/多文档切片 |
| 检索 | Recall@5 | ≥0.90 | 首选核心指标 |
| 检索 | nDCG@10 | ≥0.80 | 排序质量 |
| 检索 | MRR@10 | ≥0.75 | 首个相关排名 |
| 生成 | Faithfulness | ≥0.90 | 完整上下文、独立 judge |
| 生成 | AnswerCorrectness | ≥0.75 | reference-based |
| 生成 | AnswerRelevancy | ≥0.80 | 防止答非所问 |
| 引用 | Citation F1 | ≥0.80 | 引用必须支持句子 |
| 兜底 | 拒答正确率 | ≥0.95 | no_answer + no_invent |
| 质量 | 幻觉率 | ≤0.02 | 回答级或 claim 级 |
| 系统 | 任务成功率 | ≥0.85 | 人工/ rubric |
| 性能 | P50 / P95 | <2s / <5s | 沿用 R7/R8 |
| 成本 | cost/query | 预算内 | 按业务设定 |

> 表中数值是**首轮建议值**，必须在首轮基线 + judge 校准后评审确定；门禁采用“绝对地板 + 配对 bootstrap 95% CI 下界不低于 -ε”的双重判定，且按切片分别判定。judge 未通过人工校准前，相关指标只做观测，不设硬门禁。

### 6.4 统计规范

- **每案得分**：所有指标输出 per-case 分数，聚合用 mean/median，同时给 95% Bootstrap CI（建议 1000~5000 次，复杂统计 5000+）。
- **配对比较**：A/B（改动前后）必须用同一批用例的配对 bootstrap 或 Wilcoxon signed-rank；不要只看聚合 Δ。
- **样本量**：每个切片最小 N≥30（理想 50+），整体质量集 N≥150；核心发布集 N≥300。小样本只报 CI，不做强结论。
- **多次运行**：LLM judge 指标至少 2~3 次（或对 judge 采样），报告运行间方差；单次运行不得作为发布依据。
- **多重比较**：预注册主要指标与切片；探索性指标用 BH 校正或明确标注“探索性”。
- **冻结**：judge 模型、prompt、温度、数据集版本、语料哈希一旦冻结，跨版本结果才可比；变更需新基线。
- **拒绝 p-hacking**：不得反复调阈值/切片直到显著；不得在 holdout 上调试。

### 6.5 防作弊与防过拟合

- holdout 集绝不参与调参；发布集与开发集物理分离、查重。
- 合成用例单独打标，不能替代真实分布结论。
- 增加对抗用例：提示注入、越权、诱导编造、近重复/矛盾文档。
- 定期变异测试：验证测试套件能否发现人为引入的 bug。
- 定期人工审计：抽样核验 LLM judge 与 gold 是否仍准确。
- 隐藏集：保留一份未公开用例给外部/独立评审。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| LLM judge 偏差/方差不达标 | 质量门禁不可信 | 人工校准 + 偏差审计 + 多次运行 + 独立模型；未达标只观测 |
| 评测成本过高 | 无法日常化 | 分层运行（smoke/夜间/周度）；缓存；采样；预算告警 |
| 合成集过拟合 | 线上效果远低于离线 | 真实问句优先；holdout 冻结；线上影子评测；拒绝对 holdout 调参 |
| 数据标注质量不足 | 错误门禁 | 双人标注+仲裁；一致性指标；指南迭代；LLM 仅做候选 |
| 依赖冲突（RAGAS/LlamaIndex） | 破坏主环境 | optional extra + 独立 venv + lock + CI 安装验证 |
| 评测数据陈旧/漂移 | 指标失真 | 月度 shadow 抽样；季度重审 gold；语料版本化 |
| 测试脆弱/flaky | 团队不信任 | 隔离外部 I/O；重试与 quarantine；flake 报告与 owner |
| 隐私/合规 | 数据泄漏 | 本地 judge 优先；PII 脱敏；外部调用白名单与审计 |
| 人力不足 | 路线延期 | 先 P0/P1，质量评测从 30 条试点起步；自动化优先于规模 |
